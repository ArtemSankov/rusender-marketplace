# RuSender: верификация домена и DNS через Timeweb

## Когда применять

- Пользователь просит проверить/верифицировать домен в RuSender.
- Домен в RuSender имеет `isVerified: false` или хотя бы одна из записей `dkim`/`spf`/`dmarc` не подтверждена.
- Пользователь спрашивает, какие DNS-записи нужно добавить для RuSender.

## Жёсткие правила

1. **Токен Timeweb только от пользователя.** Не искать его в `.env`, `.env.example`, истории shell, других файлах проекта. Попросить явно: пусть пользователь вставит токен в чат. Токен не печатать в ответах, не записывать в файлы, не коммитить. Если токен пришёл в чате, передавать его скрипту только через переменную окружения в той же команде.
2. **Никаких записей без подтверждения.** Перед любым `add`/`delete` показать пользователю точный список записей (тип, хост, значение) и получить «да».
3. **Не создавать дубли SPF.** На одном хосте может быть только одна SPF-запись. Если SPF уже есть, но без `include:rsndr.ru`, предложить объединённую запись, а не вторую.
4. **Другие DNS-провайдеры не поддерживаются.** Если в NS нет `timeweb`, честно сказать: «Пока умею работать только с Timeweb», и выдать записи для ручного добавления плюс ссылку на `dashboardUrl` домена в RuSender.

## Алгоритм

### Шаг 1. Состояние домена в RuSender

Вызвать `mcp__rusender__public_domains_list` (или `mcp__rusender__public_domains_get_by_id`, если известен `domainId`). Для каждого домена посмотреть `isVerified` и `dnsRecords.{dkim,spf,dmarc}.isVerified`.

Если пользователь назвал домен, которого нет в RuSender, спросить, добавить ли его через `mcp__rusender__public_domains_create` (это создаст DKIM/SPF/DMARC записи, которые надо будет прописать).

Если все записи подтверждены, сообщить об этом и остановиться.

Собрать список недостающих записей: для каждой записи с `isVerified: false` взять `type` (всегда TXT), `host`, `data`.

### Шаг 2. Кто хостит DNS

```bash
bash .claude/skills/rusender-domain-dns/scripts/check-ns.sh <домен>
```

Скрипт поднимается по меткам домена до зоны, у которой есть NS, и печатает:

```
ZONE=example.site
NS=ns1.timeweb.ru ns2.timeweb.ru ns3.timeweb.org ns4.timeweb.org
PROVIDER=timeweb
```

`PROVIDER` бывает `timeweb`, `other` или `none` (NS не нашлись, домен, возможно, не делегирован).

Заодно проверить, что уже реально видно в DNS, чтобы отличить «запись не добавлена» от «запись добавлена, но ещё не разъехалась»:

```bash
dig TXT <host> +short
```

Если запись уже видна в DNS, но RuSender её не подтвердил, ничего не добавлять, а сразу запустить `mcp__rusender__public_domains_verify` (шаг 5).

### Шаг 3а. PROVIDER=other или none

Сообщить, что автоматическая настройка пока доступна только для Timeweb. Вывести таблицу недостающих записей (тип, хост, значение) для ручного добавления у провайдера и дать ссылку `dashboardUrl`. Предложить вернуться после добавления и запустить верификацию. Остановиться.

### Шаг 3б. PROVIDER=timeweb

1. Спросить у пользователя разрешение добавить записи через Timeweb API и попросить токен (см. правило 1). Токен создаётся в панели Timeweb Cloud, раздел «API и Terraform».
2. Проверить доступ и посмотреть, что уже есть в зоне:

```bash
TIMEWEB_CLOUD_TOKEN=... bash .claude/skills/rusender-domain-dns/scripts/timeweb-dns.sh list <ZONE>
```

Если ответ 401, токен неверный: попросить другой. Если 404 «Domain not found», домен есть в Timeweb DNS, но не на этом аккаунте: сообщить пользователю.

3. Для каждой недостающей записи вычислить `subdomain` для Timeweb: это `host` без суффикса `.<ZONE>`. Для апекса (`host == ZONE`) поле `subdomain` пустое.

   | Запись RuSender | host                              | subdomain в Timeweb   |
   | --------------- | --------------------------------- | --------------------- |
   | DKIM            | `mdmdmail._domainkey.example.com` | `mdmdmail._domainkey` |
   | DMARC           | `_dmarc.example.com`              | `_dmarc`              |
   | SPF             | `example.com`                     | пусто                 |

   Сравнить с выводом `list`. Если такая же запись (тип, subdomain, значение) уже есть, пропустить. Если на том же хосте есть другая TXT с `v=spf1`, применить правило 3 (объединить, не дублировать). Старую DKIM с тем же селектором, но другим ключом, предложить заменить (`delete` + `add`).

4. Показать пользователю итоговый план (что добавить, что заменить, что пропустить) и дождаться подтверждения.

5. Выполнить:

```bash
TIMEWEB_CLOUD_TOKEN=... bash .claude/skills/rusender-domain-dns/scripts/timeweb-dns.sh add <ZONE> TXT '<значение>' '<subdomain>'
```

Скрипт печатает созданную запись с `id`. Ошибку 409 трактовать как «такая запись уже есть».

### Шаг 4. Дождаться DNS

Timeweb отдаёт TTL 60, но резолверы могут кэшировать дольше. Проверить появление записи:

```bash
dig TXT <host> +short
dig TXT <host> @ns1.timeweb.ru +short
```

Если у авторитетного NS запись уже есть, а публичный резолвер ещё нет, подождать 1–2 минуты и повторить.

### Шаг 5. Верификация в RuSender

Вызвать `mcp__rusender__public_domains_verify` с `domainId`. Инструмент может вернуть предупреждения (например, несколько SPF) и предложенную объединённую SPF-запись: показать их пользователю и при согласии применить через `timeweb-dns.sh`.

Если после верификации остались неподтверждённые записи, сообщить какие, и предложить повторить проверку через несколько минут.

## Итоговый отчёт пользователю

- Домен, статус до и после.
- Что было добавлено или изменено в Timeweb (тип, хост, id записи).
- Что осталось неподтверждённым и почему.
- Напоминание, что токен Timeweb никуда не сохранён.
